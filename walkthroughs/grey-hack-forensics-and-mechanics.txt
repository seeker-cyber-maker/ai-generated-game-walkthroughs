-------------------------------------------------------------------------------
[03.01] MANAGED MONO RUNTIME & BINARY SEPARATION                        [ENG01]
-------------------------------------------------------------------------------

Grey Hack is developed in Unity on top of the Mono/.NET Common Language Runtime
(CLR). The game's executable architecture divides cleanly into three layers:

1. PRESENTATION LAYER:
   Unity Canvas, TextMeshPro UI, custom CRT shaders, audio mixing.
2. OS SIMULATION LAYER:
   Virtual POSIX FileSystem, Process Table, Sockets, and Router daemons.
3. SCRIPTING ENGINE:
   MiniScript / Greyscript AST Interpreter and execution sandbox.

The compiled assemblies (Assembly-CSharp.dll) contain no hardcoded single-
player mission paths; instead, the entire world is procedurally synthesized
using relational databases and stochastic network topology generators.

-------------------------------------------------------------------------------
[03.02] IN-GAME OS SIMULATION & VIRTUAL FILE SYSTEM (POSIX)             [ENG02]
-------------------------------------------------------------------------------

The in-game operating system models a POSIX-compliant file system:
• Hierarchy: /bin, /usr/bin, /lib, /usr/lib, /etc, /var/log, /home, /root.
• File Permissions: Triple-octal permission bits (rwx for User, Group, Other)
  stored as an integer bitmask (e.g. 0755, 0644).
• Process Table: Process IDs (PIDs), owner UIDs (0 for root, 1000+ for users),
  parent PIDs, memory allocation, and CPU execution slices.

===============================================================================

-------------------------------------------------------------------------------
[04.01] MINISCRIPT LEXER, PARSER & ABSTRACT SYNTAX TREE                 [LAN01]
-------------------------------------------------------------------------------

The scripting language (Greyscript) is an implementation of Joe Strout's
MiniScript embedded language engine:

1. LEXICAL TOKENIZER (Lexer.cs):
   Converts UTF-8 source code into token streams (IDENTIFIER, NUMBER, STRING,
   KEYWORD, OPERATOR).
2. RECURSIVE DESCENT PARSER (Parser.cs):
   Constructs an Abstract Syntax Tree (AST) representing expressions,
   variable assignments, conditional branches, loops, and map/list indexing.
3. EXECUTION MODEL:
   Executes via AST tree-walking and intermediate bytecode virtual machine.

-------------------------------------------------------------------------------
[04.02] GREYSCRIPT COMPILER, BYTECODE VM & SANDBOX                      [LAN02]
-------------------------------------------------------------------------------

Executing 'build /home/user/script.src /bin/script' compiles the MiniScript AST
into an optimized binary payload stored inside the target file.

SANDBOX & RESOURCE CONTROLS:
• Memory Allocation: Heap memory per script instance is bounded to prevent
  host machine memory starvation.
• Execution Throttling: Scripts yield execution every N bytecode opcodes to
  prevent infinite loops from hanging the Unity main thread.

[04.03] INTRINSICS & CORE METASPLOIT API OBJECTS                        [LAN03]
-------------------------------------------------------------------------------

Greyscript injects native C# hooks (Intrinsics) into the runtime namespace:

• metaxploit.so:
  net_use(ip, port), scan(metaLib), scan_address(metaLib, memoryAddr),
  overflow(memoryAddr, unhandledArg, extraArg).
• crypto.so:
  decipher(encryptedHash), airmon(action, device), aircrack(capFile).
• aptclient.so:
  check_upgrade, install, update, show.
• router:
  devices_lan_ip, firewall_rules, port_info, ping, bssid_name, essid_name.
• computer:
  File(path), create_folder, touch, get_ports, network_devices.
• file:
  content, set_content, chmod, delete, move, copy, is_binary.

[04.04] WRITING AUTONOMOUS EXPLOITATION SCRIPTS                         [LAN04]
-------------------------------------------------------------------------------

A clean, production-ready Greyscript auto-exploit payload:

  metaxploit = include_lib("/lib/metaxploit.so")
  if not metaxploit then exit("metaxploit.so not found")
  net_session = metaxploit.net_use(params[0], params[1].to_int)
  meta_lib = net_session.dump_lib
  memory_zones = metaxploit.scan(meta_lib)
  for zone in memory_zones
      exceptions = metaxploit.scan_address(meta_lib, zone)
      tokens = exceptions.split("<b>")
      for item in tokens
          if item.indexOf("</b>") == -1 then continue
          val = item[0:item.indexOf("</b>")]
          res = meta_lib.overflow(zone, val)
          if typeof(res) == "shell" then
              res.start_terminal
              exit()
          end if
      end for
  end for

[05.00] NETWORK STACK: MULTIPLAYER VS SINGLE-PLAYER ARCHITECTURE        [NETW]

-------------------------------------------------------------------------------
[05.01] SINGLE-PLAYER ARCHITECTURE: LOCAL SQLITE DATABASE               [NET01]
-------------------------------------------------------------------------------

In single-player mode, the entire world is stored inside a local SQLite 3
database (GreyHackDB.db):
• Tables: Computers, Routers, Files, Users, Software, NetworkPorts.
• Execution: Exploits, file writes, and process changes trigger direct SQL
  queries against the local database in real time.

-------------------------------------------------------------------------------
[05.02] MULTIPLAYER ARCHITECTURE: AUTHORITATIVE SERVER POOL             [NET02]
-------------------------------------------------------------------------------

In multiplayer mode, the client has no direct database access:
• World state is hosted on remote, authoritative database servers.
• Exploits are dispatched as RPC requests; the server verifies memory offsets
  and validates whether the library version is genuinely vulnerable.
• State changes (file deletions, log edits) sync in real time across all
  connected players.

-------------------------------------------------------------------------------
[05.03] NETWORK PROTOCOL: CUSTOM TCP / WEBSOCKET RPC                    [NET03]
-------------------------------------------------------------------------------

Multiplayer uses a binary-framed TCP/WebSocket packet stream:
  [2 Bytes] Magic Header (0x4748 - "GH")
  [2 Bytes] Opcode (Command Identifier)
  [4 Bytes] Sequence ID / Request Token
  [4 Bytes] Session Token Hash
  [4 Bytes] Payload Length (N)
  [N Bytes] JSON / Binary Serialized Payload (BSON/MessagePack)

-------------------------------------------------------------------------------
[05.04] PACKET SCHEMA & ANTI-CHEAT VALIDATION                           [NET04]
-------------------------------------------------------------------------------

• Server-Side Seed Generation: Memory vulnerability offsets are generated
  deterministically using SHA256(ServerSeed + LibraryName + Version + IP).
• Strict Session Verification: Commands to read sensitive files (/etc/shadow)
  are rejected unless the client possesses a valid server-side root session.

[06.02] LIBRARY MEMORY SCANNING (SCANLIB, MEMORY ZONES)                 [EXP02]
-------------------------------------------------------------------------------

• Using metaxploit.so, dump the target library into memory.
• scan() returns vulnerable memory segments (e.g. 0x4A2B, 0x1F8C).
• scan_address() extracts unhandled string parameters that trigger overflows.

-------------------------------------------------------------------------------
[06.03] BUFFER OVERFLOW EXPLOITATION (OVERFLOW INJECTION)               [EXP03]
-------------------------------------------------------------------------------

• meta_lib.overflow(zone, arg) corrupts target daemon memory.
• Return Types:
  - shell: Root (UID 0) or user shell.
  - computer: Direct object access to file system.
  - file: Direct reference to sensitive files (e.g. /etc/passwd).
  - null: Daemon crash; drops connection.

-------------------------------------------------------------------------------
[06.04] CRYPTOGRAPHIC CRACKING (CRYPTO.SO, HASH DECIPHER)               [EXP04]
-------------------------------------------------------------------------------

• Extract password hashes from /etc/passwd and /etc/shadow.
• crypto.decipher(hash) executes dictionary and rainbow table lookups to
  recover plain-text credentials (e.g. '123456', 'admin', 'password').
